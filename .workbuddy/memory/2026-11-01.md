## 分钟K「数据源未提供」根因（84224262）

用户报 `/api/kline/minute?symbol=002172.SZ&date=2026-10-30&live=1` 返回空、前端提示
「该日暂无分钟数据（数据源未提供）」。`data/kline_minute` 当时是空目录，但根因不是没数据，
而是 qatdx 的 `get_minute` 每次都在第一根就崩：

```
custom minute provider qatdx call failed; not falling back to TickFlow:
can't compare offset-naive and offset-aware datetimes
```

`fetch_minute_single` 传的是带 `CN_TZ` 的端点（代码注释专门解释了为什么必须带时区），
而 `qatdx.provider._bar_datetime` 明确 `replace(tzinfo=None)` 返回 naive 墙钟，
`stamp < start` 直接 TypeError；`_try_custom_minute` 的契约是 fail-closed（不跨源回退），
于是返回空 DataFrame → `source: "none"`。

### 三个独立缺陷（一起修，缺一个都还是错的）

1. **时区**：加 `_as_naive_cn()`，端点 aware → 北京墙钟 naive，与回包同口径。
2. **取数窗口**：`count` 原来按「查询区间宽度」算。pytdx 的 `start` 是「从最新一根往回数」，
   查历史某天时只取 240 根 → 永远只有最近那天 → 过滤后恒空。改成
   `span_days = today - start.date()` 倒推（自然日 ×0.8× 每天根数，上限 `_MAX_BARS=20800`）。
3. **成交量量纲**：分钟源给的是**股**，日K/面板契约是**手**。实测 002172.SZ 2026-10-30
   1m/5m/15m/30m/60m 各自求和都是 229,468,900 股，同日日K 2,294,688 手 → 差 100 倍。
   加 `_shares_to_lots()`。amount 两边都是元，不用换。

### 顺带修的 pytdx 解包残值

`pytdx.helper.get_volume` 是通达信压缩浮点解包，原始值高位字节为 0 时返回 **2^-127
(≈5.877e-39)** 而不是 0 —— 成交量为 0 的那一分钟会落成 `0 < vol < 1` 的假值。
`client.stock_bars` 里统一把小于 1 的正数归 0（最小成交单位 1 手）。

## qatdx 分钟K 的真实历史回溯上限（实测）

问题：qatdx 能不能取历史分钟K？答案：能，但窗口很窄，且是**数据源硬上限**，不是代码限制。

`client._MAX_BARS = 20800`，绕过它按原始偏移探测 `get_security_bars`：
`start=0/800/16000/20800` 都有数据，**`start=24000` 起一律返回 0 根**（80000+ 抛
`TdxFunctionCallError`）。即 1m/5m 的服务器上限就是约 20800 根。

| 周期 | 服务器给到 | 交易日 | 最早完整可用 | 早一天 |
|---|---|---|---|---|
| 1m | 20800 根 | 87 | 2026-06-25 | 2026-06-24 只有 160 根(10:51 起) |
| 5m | 20800 根 | 434 | 2025-01-14 | 2025-01-13 只有 16 根(13:45 起) |
| 15m | 8000 根 | 500 | 2024-10-10 | — |
| 30m | 4000 根 | 500 | 2024-10-10 | — |
| 60m | 2000 根 | 500 | 2024-10-10 | — |

15m/30m/60m 是服务器按「500 交易日」给的（8000/16 = 4000/8 = 2000/4 = 500）；
1m/5m 是按「20800 根」给的（434 < 500，所以 5m 没顶到 500 天）。

越界日期经 `provider.get_minute` 返回空 DataFrame，耗时约 1.0s（clamp 到 20800 根、
26 页翻完才发现过滤后为空），不报错、不卡死。

**关键含义**：1m 只有 4 个月滚动窗口，错过就永久拿不回。要做分钟级回测/落盘，
必须自己定期增量落盘（`data/kline_minute` 现在只有 9 分区 × 1 只，是页面按需写的，
全市场分钟数据为空）。5m 可补 1.8 年，15m+ 可补 500 个交易日。
其他数据源当前全 unavailable（akshare/eltdx/fuyao/tdxquant 均 False），没有替代。

## 更正：上一节「数据源硬上限」的结论是错的

我上面写「20800 根是数据源硬上限、没有替代」——**错的**。20800 只是
`get_security_bars`（K线接口）单次可取的最大根数，通达信还有两个**按日期取**的接口，
完全不受这个限制：

| 接口 | 深度（实测） | 返回字段 | 成本/股/天 |
|---|---|---|---|
| `get_security_bars` | 1m 20800根(87天) / 5m 434天 / 15m+ 500天 | 完整 OHLCV+amount | 0.06~9s |
| `get_history_minute_time_data(market, code, "YYYYMMDD")` | **2007-01-04 起**（2006-01-04 返回 0） | 仅 `price` + `vol`，240 条 | **0.02s** |
| `get_history_transaction_data(market, code, start, count, date)` | **至少 2008-01-02 起** | `time/price/vol/buyorsell` 逐笔 | 0.12s（约 3 页） |

### 对齐关系（这是能不能用的关键）

- 分时的第 i 条 `price` = 官方 1m K 第 i 根的 `close`，**240/240 全对，无偏移**
- 逐笔按 `time` 分钟聚合，聚合桶 **T 对应官方分钟K 的 T+1 分钟**（整体错 1 分钟）。
  按 +1 对齐后 240 根里 **236 根 OHLC 完全一致**，成交量仅 3 根不一致（09:30 集合竞价、
  11:29、14:59 边界）。所以逐笔能重建几乎完美的官方 1m K。
- 单位：逐笔 `vol` 是**手**，官方分钟K `vol` 是**股**（差 100）。逐笔 `price*vol*100`
  估算成交额 2,152,879,404 vs 官方 2,152,393,879，差 0.02%。

### QUANTAXIS 为什么也拿不到长历史

它 `QA_fetch_get_stock_min` 里明写 `if lens > 20800: lens = 20800`，只走
`get_security_bars`。全仓库 grep `get_history_minute_time_data` **零命中** —— 上游没用过
分时接口。用户记得的「QUANTAXIS 能取所有时间段」，实际对应它另一条路
`QA_fetch_get_stock_transaction`（历史逐笔，`get_history_transaction_data`），那条确实能回溯。

## 历史分钟通道已接入（071baa0d）

**client.py**
- `history_minute_time(market, code, dates)` → `get_history_minute_time_data`，一次

  连续跑多个频率时全部 0 根）。现在 `_call(fn, need_history=True)` 时额外用

## qatdx 全能力体检 + 6 处取数缺陷修复（commit b92adee8）

体检方法: 26 项能力逐个打真实主站（不走 HTTP 层、不打桩），逐项记录现象/耗时/根因。

### 硬事实（后续改动不要再猜）
- **指数必须走 `get_index_bars`**。指数回包尾部多 up_count/down_count，用股票的
  GetSecurityBarsCmd 解出来是 `year=395942 / open=-76257`，provider 按日期过滤后
  恒为空且**不抛错**。旧代码对指数统一用 get_security_bars，被上层回退 TickFlow
  掩盖了整整一层（kline_index_daily 的 599 只全是 TickFlow 落的）。
- **板块记录步长 2813**（9 名称 + 2 成分数 + 2 类型 + 400×7 代码槽）。四个 block
  文件均满足 `386 + num*2813 == size`。pytdx 原实现写死 2800。
- **`get_block_info` 每页回 60000 字节**（不是包里的 0x7530=30000）。pytdx 的
  `get_and_parse_block_info` 按 30000 推进会请求到上一页中间，拼出重叠文件 →
  block.dat 出 80 万行垃圾。正确做法是**按实际回包长度推进**，不设步长常量。
- `tdxhy.cfg` 10218 行 / 112 个行业代码，**全文 0 行含中文**；`incon.dat`、
  `tdxzs.cfg` 的 meta size 都是 0。行业中文名只在客户端本地文件里，服务端没有。
- 主站历史覆盖深度不同：`119.97.185.59` 有 2024-01-02 分时但 2015/2008 全空；
  `218.106.92.182`/`180.153.18.170` 能到 2008。**探测点必须跟着请求的最早日期走**，
  缓存要带「可查下限」(history_from)，否则远期查询随机返回空。
- 日线 count 是「从最新往回数 N 根」，必须按 (today-start) 算；8000 根可回溯到
  1991（offset=7600 落在 1991-07-30）。
- 上交所融资融券 xls：明细在第二个 sheet（约 2017 行 × 8 列，首行即数据），
  单元格是 **UTF-16LE 字节被按 latin-1 逐字符读出**（"510050" → "5\x001\x000…"），
  要 `encode("latin-1").decode("utf-16-le")` 还愿；列序 代码|简称|融资余额|
  融资买入额|融资偿还额|融券余量|融券卖出量|融券偿还量。
- 深交所融资融券：`ShowReport.szse` 已 404；用 `ShowReport/data?SHOWTYPE=JSON
  &CATALOGID=1837_xxpl&txtDate=&tab2PAGENO=`，明细每页固定 20 行（pageSize 参数
  无效），metadata 里有 pagecount。字段 jrrzye/jrrzmr/jrrjmc/jrrjyl 单位是
  亿元/亿股，要 ×1e8。并发 16 会 502，并发 8 + 重试 3 次 + 失败页补抓才稳
  （漏页会静默少 358 只）。
- ETF 不能按简称判：通达信列表里 159915 叫「创业板」、588000 叫「科创50」。
  必须按**市场 + 代码段**：深市只认 15x；沪市 510~518/520~522/560~566/588/589。
  520/563 在深市是债券（"26伊犁02"/"山西2430"），不分市场会收错。
- 北交所 market=2：pytdx 这批主站一律 `TdxFunctionCallError`，0 台支持。
- 主站协议握手并行后冷启动 9.1s → 4.8s。

### 修复后实测
指数日线 1992-2026 可取、指数分钟正常；板块 90778 行/533 板块；行业 5587 行；
日线 2015/2008 区间有数据；2015 分钟 960 行 ×3 次稳定；融资融券 4135 行；
ETF 1773 只（9 只主流全在）；test_dataset 13 项全通。

### 仍是源头不提供（如实标注，不要再当作 bug 修）
财务明细(仅股本)、行业中文名、北交所。

### 测试基线
qatdx 单测 36 passed。全量 4419 passed / 31 failed —— 这 31 个在**未改代码时
同样失败**（Windows 软链/权限类 + 上游既有），用 `git stash` + `pytest --lf`
对比确认过，不是本次引入。

## eltdx 全能力体检 + 日K深度三处连坐缺陷修复

体检方法同 qatdx: 起 eltdx HTTP 网关(127.0.0.1:8000), 逐项打真实网络。
**注意**: 网关平时不在跑, 复测必须先用
`(backend/.venv/Scripts/python.exe -m eltdx.http_server --host 127.0.0.1 --port 8000 &)`
拉起来, 且后台任务的子 shell 结束会把网关带走 —— 后续脚本会各自秒拒连。

### 硬事实（后续不要再猜）
- **`bars.get` 单请求上限 800 根**, 与批量标的数无关。`count>800` 直接 HTTP 400
  "page size must be between 1 and 800", 上层只看到一条 warning + 空表。
- **`start` 语义是「从最新往回数」的偏移**, 每页**页内升序**。所以跨页拼成时间序列
  必须**页倒序拼接**(`_pages_to_series`), 依次追加会得到「新段升序+老段升序」的锯齿。
  单标的 `bars` 与批量 `bars_multi` 两条路径原本都是错的。
- **`bars.get` 有 800 上限这件事与传输方式无关**: 进程内 `EltDxClient` 与 HTTP
  `HttpTransport` 都要自己分页; 进程内 `iter_bars_batches` 走的是逐标的 `bars`
  (已分页)所以没暴露, HTTP 的 `iter_bars_batches` 直接调 `bars_multi` 就炸。
- count 必须**从今天倒推到 start**, 不能按查询区间宽度。按宽度算: 查 2015Q1 只回
  最近 ~129 个交易日, 过滤后 0 行。同一根因还打在除权因子的 lookback 上
  (查 2015/2005 全年 0 行, 因为找不到事件日前一交易日收盘)。
- 快照 JSON **没有 `change_pct` 这个键** —— SDK 里它是 `@property`, dataclass
  序列化不带, 所以 HTTP 传输下 `getattr(snap,"change_pct")` 恒 None。进程内有值。
  契约要求该字段可用 → 用 `(last-prev)/prev` 补算(小数制)。
- 快照 `total_hand` 是手、`amount` 是元; `change_pct` 若真有值是**百分数制**要 /100。
- `get_minute` 的 `freq` 原先被忽略(一律返回 240 根 1m) —— 这会让调用方把 1m 当
  60m 落表, 属静默数据错误。改为本地按交易时段分桶重采样。
- 设置页试拉测试的 minute/full_minute/auction 原先都按 `date.today()` 取样,
  周末点测试恒 0 行、与故障无法区分 → 改按 `_latest_business_day()`。

### 修复后实测（真实网络, 2026-11-01 周日）
- 日K 3.8 年跨度: 0 行 → **925 行**; 2015Q1: 0 → **57 行**; 2008 全年: **245 行**;
  全历史(1991起, 上限 8000 根): **8000 行**(1993-03-15..2026-10-30)
- 除权因子 2015 全年: 0 → **1 行**; 2005 全年: 0 → **1 行**; 近 6 年 11 行
- 除权因子与本地表对账: 重叠 2 行, 最大相对误差 **0.000357%**
- 1m 单日 240 行(量合计 59927 手) → 5m **48 行**、30m 8 行、60m 4 行,
  **量合计仍 59927**（重采样守恒）；`freq=7m` fail-closed 返回空帧
- `get_minute(datetime(2026,10,30), datetime(2026,10,30))`: 0 行 → **240 行**
  (原 `_as_datetime` 对 datetime 入参忽略 end_of_day, 区间退化成 [00:00,00:00])
- 实时 change_pct: None → 0.028102(茅台) / 0.008666(平安)
- test_dataset 8 项在周末全部有行: daily 17 / realtime 20 / minute 240 /
  full_minute 10 / depth5 1 / auction 82 / financial 1 / adj_factor 4

### 口径统一
新增 `app/plugins/minute_bucket.py`(CN_SESSIONS / session_bucket / session_minutes /
resample_minute), qatdx 与 eltdx 共用；qatdx 的 `_session_bucket` / `_session_minutes`
/ `_resample_bars` 保留为薄包装（既有测试按这些名字导入）。

### 仍是源头边界（不是 bug）
1m 深度上限 12000 根 ≈ 50 交易日；竞价约 12 个月回溯；income/metrics 上游无数值；
快照不带 name/amplitude/turnover_rate；北交所日K/分钟/盘口可用但无竞价。

### 测试基线
eltdx 174 → **186 passed**（新增 12 个回归：count 起点、lookback 起点、双传输分页、
页序、change_pct 推导、end_of_day、freq 重采样与午休分桶、取样工作日）。
qatdx 仍 36 passed。
