## eltdx 插件「安装成功但不能启用」排查（已解决）

- 现象：设置 → 数据源，eltdx (通达信) 点「安装依赖」提示成功，卡片仍灰显不可选。
- 根因：**安装按钮只执行 `pip install eltdx`（装 SDK），不装也不启动 HTTP 网关**。而插件
  `availability()` 默认 `ELTDX_TRANSPORT=http`，必须探到 `http://127.0.0.1:8000/health` 才判可用；
  网关没起 → `ConnectionRefusedError` → `available=false`。前端 `DataSources.tsx:797`
  `if (pluginUnavailable && !plugin?.api_key_env) return`（eltdx 无 api_key_env）→ 卡片整块不可点。
- 已做的修复（未改任何仓库代码）：
  - 确认 SDK 已装好：`backend/.venv` 内 `eltdx 3.3.2`，`eltdx.http_server` 可导入（网关依赖 fastapi/uvicorn 已在 venv 里，无需装 `eltdx[http]`）。
  - 启动网关：`cd backend && ./.venv/Scripts/eltdx-http.exe --host 127.0.0.1 --port 8000`
  - `POST /api/settings/data-sources/reload` 后插件状态变为 `ok (eltaX 网关 3.3.2 @ http://127.0.0.1:8000)`，`available=true`。
  - 端到端验证：网关 `POST /rpc quotes.get_snapshots {"codes":["sz000001"]}` 返回真实快照（last_price 11.64 / pre_close 11.54）。
- 遗留问题（产品缺陷，未修）：
  - `backend/app/plugins/eltdx/plugin.yaml` 的 `install_hint` 只提 `pip install eltdx`，没提必须起 `eltdx-http`；报错文案里指的 `docs/HTTP_GATEWAY.md` 在仓库里不存在，实际只在 `site-packages/eltdx/docs/` 下。
  - 网关是外部 sidecar，`dev.sh` / `dev.ps1` 均不管它；机器重启后 eltdx 会重新变不可用，必须手动起网关。
  - 备选 `ELTDX_TRANSPORT=inproc` 可在进程内直连，但代码注释明确警告「运行时崩溃牵连全部数据集 + 多进程踩踏」，**不推荐**。

## qatdx「同步 0 只标的」根因排查（三个独立缺陷叠加）

现象：12:02 数据同步 → 个股维表同步完成「0 只标的」→ 标的池 0 → 日K「完成」但什么都没拉。

**缺陷 1（表层）**：`vendor/pytdx/pytdx/parser/get_security_list.py` 用 `decode("gbk")` 严格解码
8 字节 name 字段。中文名超过 4 字会被协议从中间截断，半个汉字的字节让 strict decode 抛
`UnicodeDecodeError` → 整页（最多 1000 只）解析失败 → 三个市场全挂 → 维表 0 行。
→ 改成 `errors="ignore"`（丢掉残缺尾字节）。

**缺陷 2（数据污染）**：`_asset_kind` 只看代码前缀不看市场。沪市列表里 000xxx（上证系列指数）、
880xxx/881xxx/888xxx（通达信板块与统计指数）全被当成股票 → 维表 3639 只沪市里 1320 只是假的，
会经标的池进 kline_daily。→ 改成按市场判断：沪 `60/68`、深 `00/30`、北 `43/83/87/88/92`。
修完维表 = 5225 只（沪 2319 + 深 2906，**北交所列表接口在该主站超时，缺失**）。

**缺陷 3（协议层，最隐蔽）**：pytdx 的三段握手里 `SetupCmd3`（携带十几年前的客户端授权串）
会让**当前主站把连接降级**：security_count / security_list / get_xdxr_info / get_finance_info
照常可用，但 0x052d(K线) / 0x053e(报价) / 当日分笔一律只回 2 字节「计数=800、零记录」的空页，
pytdx 侧报 `TdxFunctionCallError: unpack requires a buffer of 4 bytes`。
- 排除法：111 个主站里 29 个可达，**全部**同样报错；换成 eltdx 自己用的 10 个主站也一样；
  PyPI 官方 pytdx 1.72 结果完全相同 → 不是本项目 vendor 分叉的锅，也不是网络/主站故障。
- 定位方法：写了个 TCP 代理（`.workbuddy/tmp/tdx_proxy.py`）把 eltdx 的真实报文抓下来做字节对比，
  发现 K 线请求体/头都对得上，唯独握手不同。逐步二分：S1 正常、S1+S2 正常、S1+S3 退化为空页。
- → `hq.py` 的 `setup()` 默认只发 S1+S2，需要兼容旧主站时置 `TDX_LEGACY_SETUP=1`。
- 修完日K/分钟/指数/报价/分笔/财务全部恢复（实测茅台 1392.05，与 eltdx 一致）。

**附带的第 4 个 bug**：`client.stock_bars` 取回「最近 800 根」那一页后直接 `[:count]` 截断，
拿到的是页内**最旧**的 count 根（count=30 会取到三年前的 30 根），调用方按日期区间过滤就成空表。
→ 改为统一排序后取 `rows[-count:]`。

**性能坑**：`_persist_daily_chunks` 会按日期拆分落地，provider 一只一帧时变成
「股票 × 交易日」≈ 125 万个小 parquet，实测 5 分钟只推进 37 只。→ qatdx `iter_daily`
改成 200 只合并一帧（`_DAILY_CHUNK`），5000 只全市场首次同步从「十几小时」降到「约半小时」。

验证：`tests/test_qatdx_instruments.py` 6 条 + 既有 5 条 = 11 passed；ruff 改动文件 0 新增告警。
**踩坑**：uvicorn `--reload` 对本机 `backend/` 的改动**不会真的热重载**（日志里没有 Reloading，
跑的还是旧代码），改完必须 taskkill 端口进程再重启，否则会被"改了没生效"误导很久。

## /api/data/status 30s 超时排查（2026-10-31 夜，未修复）

**根因：`data/kline_daily` 有 62,943 个 `part-stream-*.parquet` 碎片**（2671 个交易日 × 约 23 片），
正规的 `part.parquet` 只有 1 个。`kline_daily` 是 DuckDB `read_parquet('**/*.parquet',
union_by_name=true)` 视图，每次查询都要展开 glob + 打开全部 6.3 万文件读 footer。

实测（独立 duckdb 进程，backend/.venv）：
- kline_daily      62944 文件 / 1065 万行 → count(*) 47.6s，完整聚合 37.0s，union_by_name=false 22.8s
- kline_daily_enriched 242 文件 / 125 万行 → 1.65s
- kline_etf_daily     242 文件 / 36 万行 → 0.90s
- instruments          1 文件 / 5225 行 → 0.02s
→ 瓶颈是**文件数**不是行数，约 0.75ms/文件。

**为什么必超时（三数叠加）**：单次聚合 37~48s > 前端 axios 30s 超时；`_TABLE_TTL = 30s`
比计算还短 → 缓存**永远不可能命中**，每轮全量重算；`Data.tsx:88` 轮询 30s，上轮未完成下轮已发，
在 repository DuckDB 单连接全局锁上排队。直连 3018 curl 70s 不返回，同时 /api/health 1.08s、
/api/strategies 0.2s 正常 → 后端没死，是这个端点在自我排队。

**碎片来源**：`backend/app/services/kline_sync.py:407 _persist_daily_chunks`。staging 阶段每个
chunk（200 只/批，约 26 批）对同一日期写 `part-{index}.parquet`；提交阶段若 `existing` 为空，
把这 26 个分片**逐个 rename 成 part-stream-0..25**（而非合并）。注释宣称"每天一个文件"的
`_write_daily_partition` 只在 existing 非空时被调到。历史日期之后不再写入 → 碎片永久残留。

**修复方案（用户选「先不动」，尚未实施）**：
1. 一次性合并：每个日期目录 26 片 → 单个 part.parquet（62943→2671），预计聚合降到 2~3s
2. `_persist_daily_chunks` 首次写入分支改为 `repo.append_daily(merged)`，不再产生碎片（约 5 行）
3. `_TABLE_TTL` 30s → 300s（1 行），配合第 1 步后请求基本 O(1)
注意：合并期间须停后端写入；写 tmp 后 os.replace 保证原子性；临时磁盘开销可忽略。

## kline_daily 碎片归因补全（2026-11-01 深挖 PR #493）

昨天只查到「4d53f66c 引入 rename 分支」，今天补上归因的四层，都在提交 `4d53f66c`
（PR **#493**，merge commit `20a36681`，Zhangergou，2026-10-19 15:40）里：

**改动本体**：`_persist_daily_chunks` 提交阶段从
`repo.append_daily(scan_parquet(files))`（合并成 1 个 part.parquet）
改成两分支 ——
- `existing` 为空：`for i, staged: replace_with_retry(staged, target/part-stream-{i}.parquet)`
  → **N 个文件直接 promote，不合并**
- `existing` 非空：scan 旧+新 → concat/unique → append_daily(1 个 part.parquet) →
  `for part in glob("part-stream-*"): unlink()`（清理上一支留的垫片）

**为什么没被发现（四层，缺一层都不会发生）：**
1. **benchmark 只测写不测读**：`backend/scripts/benchmark_daily_sync_staging.py`
   只对比 `read-back-and-rewrite` vs `direct-copyfile` 的耗时（4 片/10 万行），
   输出命名直接是 `promoted-{index}.parquet` —— 作者把 **N 文件当成正确产出形态**，
   测量维度里根本没有「读这 N 个文件要多久」。
2. **测试主动锁定错误行为**：新增 `test_sync_promotes_staged_files_without_reading_them_back`，
   断言 `len(parts) == 2`，并用 monkeypatch 让 `kline_sync.pl.scan_parquet` 直接抛
   `AssertionError("不应读回临时文件")` —— 不是遗漏，是把「不读回 + 多文件」写成契约。
   同时把老测试 `test_sync_persists_streamed_fuyao_chunks_only_after_fetch` 的
   `read_parquet(.../part.parquet)` 放宽成 `concat(glob("*.parquet"))`。
   同函数两条分支形态不同（A 出 N 个 / B 出 1 个），各有测试且都绿，
   **没有测试断言两者形态一致** ← 真正的设计缺口。
3. **绕过了既定契约**：`repository._write_daily_partition` docstring 明写
   「每个日期一个文件，支持 merge-upsert」，分支 A 完全绕过它。
4. **触发源差异**：`fuyao.iter_daily` 在 `_RECENT_DUMP_DAYS=12` 内一次 dump 全市场、
   **只 yield 1 个 chunk** → 近期同步时每日期只有 part-stream-0，文件数不增加，
   肉眼与 part.parquet 无区别。只有**长窗口全量回填**才会暴露：fuyao 按 dump/api 切多源、
   qatdx 改动前更是 `for symbol: yield frame`（一只一帧 → 5225 个 chunk）。

**碎片数 = 交易日期数 × 该日期有数据的 chunk 数**：
62943 = 2671 天 × 平均 23.6（qatdx 5225 只 / _DAILY_CHUNK=200 上限 27 批，
空 chunk 被 `if df.is_empty(): continue` 跳过，故实际略低）。只有一个日期
（date=2025-10-31，被二次写入）走了分支 B，留下单个 part.parquet，是唯一反证。

**教训**：存储布局的优化不能只基准写侧；文件数本身就是读侧成本（DuckDB 逐文件读 footer）。
