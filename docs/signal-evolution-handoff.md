## 4. 当前进化链路的真实实现

### 4.1 前端入口

主要调用链：

```text
frontend/src/custom/research-workbench/extension.tsx
  -> Workbench
  -> frontend/src/custom/research-workbench/recipes/daban.tsx
  -> frontend/src/custom/research-workbench/recipes/TagEvolution.tsx
  -> api.dabanResearchEvolution()
```

相关文件：

- `frontend/src/custom/research-workbench/recipes/TagEvolution.tsx`
- `frontend/src/custom/research-workbench/recipes/daban.tsx`
- `frontend/src/lib/api.ts`

当前页面问题：

- `TagEvolution`没有接收打板研究页的筛选条件、日期、板块位置或退出模式；
- 候选数量和耗时文案写死为 `144` 个事前文字，即72个旧标签的正反向；
- “重新搜索”只设置 `ran=true`，查询参数未变时不一定产生新请求；
- 页面“最佳”按全样本胜率选择，后端实际按score排序，前后端口径不一致；
- 没有保存研究候选、冻结结果或发布审核入口。

### 4.2 后端入口

主要调用链：

```text
GET /api/daban-research/evolution
  -> backend/app/api/daban_research.py
  -> backend/app/services/daban_tag_evolution.py::run_evolution()
  -> data_dir/daban_research/stats.parquet + tags.parquet
```

当前服务仍然是同步GET搜索，没有任务状态、取消、快照和候选保存接口。

### 4.3 旧搜索实际做的事情

`backend/app/services/daban_tag_evolution.py`：

- 读取旧的 `daban_compute.TAG_DEFS`；
- 只取 `timing == 'pre'` 的旧标签；
- 每个标签生成正向和反向两个term；
- 最多组合3个term；
- 用触板研究缓存中的 `r_t1` 评价；
- 全样本评分，再用OOS退化进行折扣；
- 结果直接返回页面展示。

因此它不是“新增因子自动生成信号”的实现。

## 5. 已确认的源码风险

以下结论来自静态源码复核，本轮没有重新运行进化任务，也没有统计真实受影响行数。

### 5.1 旧输入不是迁移后的普通信号

`_term_masks()`读取旧位图，不读取：

- `factors/registry.py`中的因子注册表；
- `strategy/custom_signals.py`中的普通信号；
- 新迁移的严格三态信号；
- 新增因子生成的阈值候选。

### 5.2 未知会被错误取反

旧标签缺少数据时可能按未命中保存，随后使用 `~base` 生成反向term。这样“未知”可能变成“非该条件成立”，产生错误命中。

新实现必须保留：

```text
value + valid
```

未知不能等价于false，更不能等价于NOT true。

### 5.3 缺失收益哨兵过滤存在风险

`daban_compute.I()`使用 `-9999` 表示缺失，旧搜索先除以100再执行 `r1 > -9000`。因此 `-9999 / 100 = -99.99`，仍然会通过该判断。

本风险已记录，但不要在新任务中直接大范围修旧研究缓存，除非用户另行批准。

### 5.4 样本外参与搜索选择

旧搜索用全样本胜率和均值作为主要评分，再用OOS表现进行惩罚。OOS并不是冻结后的独立留出评价。

新链路必须：

- 只在训练段拟合阈值；
- 只在训练段生成、扩展和排序候选；
- 留出段只评价已经冻结的候选；
- 不能根据留出结果重排或删选候选。

### 5.5 事件样本与普通选股样本混淆

旧研究数据来自触板/涨停事件样本，不是全股票×交易日候选池。旧收益也对应事件日涨停价到后续收盘，不能直接解释为普通日线信号的可交易收益。

新研究建议采用：

- D日收盘已知的数据；
- 股票×交易日研究面板；
- 固定的未来1/3/5交易日收盘收益；
- 研究收益与真实交易PnL明确分开。

### 5.6 键和代次对齐不充分

`_load()`只校验 `stats` 和 `tags` 行数相等，没有验证：

- 股票代码；
- 交易日期；
- 数据快照/生成代次；
- 重复键；
- 计算日历。

新链路必须按证券和交易日键对齐，拒绝混代或重复数据。

### 5.7 运行方式不适合重型研究

当前进化是同步GET，且会修改模块级 `MIN_SAMPLES`。不适合扩展为真正的因子搜索。

新任务应使用已有：

- `backend/app/services/pipeline_jobs.py`
- `backend/app/services/heavy_job_limiter.py`
- 现有取消和任务状态机制

不要在GET请求里直接启动长时间搜索。

## 6. 推荐实施方案：第一阶段最小闭环

这是下一阶段建议实施的内容，**尚未获得实施确认**。

### 6.1 第一阶段目标

打通以下最小链路：

```text
隔离定义快照
  -> 选择一个普通信号 + 一个已有数值因子
  -> 训练集生成有限阈值候选
  -> 生成正向AND组合
  -> 冻结候选
  -> 留出集评价
  -> 保存可复现研究结果
```

推荐使用已有 `amihud_20d` 作为贯通样例，仅验证机制，不代表它等价于小市值。

### 6.2 输入

- 研究定义使用隔离快照；
- 显式选择已批准迁移集合；
- 同ID同内容可去重；同ID不同内容必须报冲突；
- 不安装生产定义、不修改全局因子注册状态；
- 不要求全部93个信号都有真实数据后才开始小规模研究。

### 6.3 候选生成

第一版仅支持：

- 一个数值因子；
- 训练集20/40/60/80分位阈值；
- `factor >= threshold` 和 `factor <= threshold`；
- 阈值去重；
- 组合最多3个正向信号；
- 展开后的普通条件不超过8个。

首版暂不支持：

- 任意OR；
- 复合信号整体NOT；
- 自动生成任意Python表达式；
- LLM直接生成可执行公式；
- 自动发布策略。

原因：普通信号现有合同是有限AND条件，`NOT(A AND B)`不能错误实现成 `NOT A AND NOT B`。

### 6.4 三态规则

每个因子/信号都要保留：

- 值；
- 有效性；
- 缺失原因或来源状态。

组合规则：

- 任一输入未知，组合结果为未知；
- 只有所有输入已知时才计算AND；
- 报告命中、未命中、未知和目标缺失数量；
- 不把未知填成0、false或反向命中。

### 6.5 时间和目标

建议：

- D日收盘可知特征；
- 主目标固定为未来3个交易日收盘收益；
- 1日/5日收益只作辅助展示；
- 用真实交易日历按日期连接，不用证券行号shift；
- 跨训练/留出边界的收益样本进行purge。

这只是研究关联指标，不等于按D日收盘可以成交的实际策略收益。

### 6.6 训练/留出

建议按唯一交易日期切分：

- 前70%日期训练；
- 后30%日期留出；
- 阈值、方向、候选扩展和排序只使用训练集；
- 留出只用于冻结候选的评价；
- 留出不足时明确标记不可评价，不当作失败或成功；
- 后续如要晋级策略，仍需独立外层验证和执行模型。

### 6.7 任务和结果

不要继续扩展同步GET。建议：

- POST创建研究任务；
- GET查询任务状态和结果；
- 支持取消；
- 使用现有任务/重型任务限制；
- 单任务、单worker、有限搜索预算；
- 记录定义hash、依赖hash、数据代次、日历、证券范围、目标、阈值、参数和版本；
- 取消、超时、异常结果不能当作成功结果。

首阶段只保存研究快照和结果，不直接写入生产普通信号，也不进入策略发布库。
