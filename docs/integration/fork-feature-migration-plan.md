## 1. 目标与范围

本轮目标是将 15 个 Fork 中经过提交 SHA 与 stable patch-id 匹配后确认的 Fork 独有改动，按业务依赖分层评估并逐批迁移到 `fork-integration`。迁移顺序固定为：

```text
数据底座与数据源
  -> 策略、指标与因子
  -> 回测与研究
  -> 持仓、模拟盘与风险
  -> 监控、AI 与前端集成
  -> 部署与发布
```

本计划只授权**规划、去重、证据整理和分批迁移设计**，不授权未经单批确认的业务代码修改、reset、rebase、强制推送或整 Fork 覆盖。

### 1.1 当前分析规模

- 原始独有提交：`2,770` 条；
- 启发式功能组：`895` 组；
- 覆盖 Fork：`15` 个；
- 功能识别结果：895 组中 `258` 个高置信度、`612` 个中置信度、`25` 个低置信度；
- 当前结果是候选清单，不等于已确认功能总数；同一功能在多个 Fork 中重复出现，后续必须建立全局功能 ID 并去重。

### 1.2 不纳入业务迁移范围的内容

除非单独确认，不迁移以下内容：

- README、截图、营销文案和纯文档排版；
- 任务归档、研究日志和生成的分析 CSV；
- 无业务含义的打印语句或格式化；
- 未审核的 vendor 整目录、第三方代码和二进制数据；
- 未证明与当前主线兼容的 Docker/CI 旁路脚本；
- 仅由提交标题推断、没有路径或 diff 证据的低置信度功能。

### 2.1 本地源码快照与迁移溯源

迁移实施前，必须把涉及功能的源仓库源码下载到本机仓库之外的临时目录，并以固定 SHA 的本地源码快照、原始提交 diff 和配套测试作为唯一实现依据。功能识别 CSV 只用于定位候选，不得替代源码审阅。

**源码快照约定**：

- 快照必须存放在本仓库之外的临时目录，不得写入 `analysis/`、`docs/` 或其他项目目录；
- 推荐根目录：`${TMPDIR:-/tmp}/tick-stock-panel-fork-migration/`；
- 单仓库目录：`<owner>__<repo>/<commit_sha>/`；
- 每个快照必须保留仓库地址、分支、固定 SHA、获取时间、Git 版本和工作树状态；
- 每次迁移批次必须在任务台账记录临时快照的绝对路径、manifest 和固定 SHA；
- 迁移任务未完成或未人工确认前，不得清理对应临时快照；临时目录丢失后必须使用同一 SHA 重新下载并重新核对；
- 源仓库更新或更换基线时，创建新的临时快照和迁移轮次，不覆盖既有快照。

**迁移前强制流程**：

```text
固定仓库/分支/SHA
  -> 下载本地源码快照
  -> 检查源码、原始提交 diff 和配套测试
  -> 对比目标主线调用链和契约
  -> 确认功能边界及依赖
  -> 按原始实现移植
  -> 仅做有证据的最小兼容修改
  -> 运行原测试和目标主线定向验证
```

**禁止事项**：

- 未下载并核对源仓库源码前，不得开始业务代码迁移；
- 不得仅根据提交标题、功能识别结果或 README 自行重写功能；
- 不得整体复制 Fork、覆盖目标主线或混入未批准的无关提交；
- 不得为了“适配方便”另写一套与源实现并行的策略、数据源或回测逻辑；
- 只有当前主线存在明确接口、目录、数据字段或安全契约不兼容时，才允许做最小兼容修改；
- 任何兼容修改都必须记录原始代码位置、目标修改位置、修改原因和验证结果。

**每个功能的溯源记录至少包含**：

- `global_feature_id`；
- 源仓库 URL、分支和固定 SHA；
- 本地源码快照路径；
- 原始提交 SHA、父提交和原始提交 message；
- 原始变更文件和配套测试；
- 目标主线对应文件和调用链；
- 是否直接移植、最小兼容修改或阻塞；
- 所有兼容修改的原因、范围和风险；
- 原测试、目标测试、验证命令和实际结果。

未完成本地源码快照、原始 diff 或配套测试核对的功能，状态必须保持为 `待源码审计` 或 `阻塞`，不得标记为 `代码已移植`。

## 3. 迁移判定与证据规则

### 3.1 迁移单位

不以单个 commit 作为默认迁移单位，而以“功能组”作为迁移单位：初始实现、后续修复、测试和必要配置必须先归并，再决定是否迁移。每个功能组必须关联：

- `feature_id`；
- Fork 与分支；
- 原始 commit SHA；
- 原始提交标题和完整 message；
- 原始修改路径；
- 后续修复和测试；
- 当前主线重叠情况；
- 源码快照路径和快照 SHA；
- 原始代码位置与目标代码位置；
- 兼容调整位置及调整原因；
- 原始测试、目标测试、验证命令和结果。

### 3.2 判定状态

| 状态 | 含义 |
|---|---|
| `待去重` | 多个 Fork 可能是同一功能，尚未建立全局功能 ID |
| `待源码审计` | 已定位候选，但本地源码、原始 diff 或配套测试尚未完成核对 |
| `待迁移前确认` | 已完成源码审计，已准备迁移说明，等待用户明确确认 |
| `待迁移` | 已获得迁移前确认，功能边界可独立迁移 |
| `迁移中` | 已确认本批范围，正在按原始代码和测试实施 |
| `代码已移植` | 原代码已落地，但未完成完整验证 |
| `已验证` | 通过目标模块、兼容和失败路径测试 |
| `无需迁移` | 主线已有等价能力，或仅为文档/生成文件 |
| `阻塞` | 依赖、数据口径、许可或资源条件未满足 |

### 3.3 迁移前用户确认门禁

每个功能开始迁移前，执行者必须先向用户说明该功能的迁移意义、解决的问题、预期获得的能力、来源仓库和主要风险，并等待用户明确确认。未获得确认前，只允许进行只读分析、源码下载和证据整理，不得修改目标代码、配置、数据或启动该功能的迁移。

**迁移前说明至少包含**：

- 功能名称、`task_id` 和 `global_feature_id`；
- 源仓库、分支、固定 SHA 和本地临时快照路径；
- 为什么要迁移：当前主线缺口、业务价值和依赖位置；
- 用户将得到什么：可使用能力、覆盖场景和明确边界；
- 将修改的目标文件或模块范围；
- 已知风险、兼容性问题、数据口径影响和回滚边界；
- 预计验证方式和人工确认点。

**确认结果**：

- `确认开始`：允许进入该功能的代码迁移；
- `暂不迁移`：保持任务待处理，记录用户意见；
- `需要调整范围`：不得开始迁移，先更新方案并重新说明；
- 未明确回复：视为未确认，不得开始迁移。

用户确认必须记录在任务台账中，至少包含确认范围、确认内容、确认时间、目标基线和用户原始确认摘要。确认只对明确列出的单个功能或功能批次有效，不自动授权其他功能。

### 3.4 人工确认门禁

每个功能组必须独立完成“迁移前用户确认、源码移植、自动验证、迁移后人工确认”四步，未经迁移前确认不得开始，未经迁移后人工确认不得开始下一功能迁移。人工确认不是形式性签字，而是对当前功能范围、源码来源、兼容修改、验证结果和剩余风险的明确审核。

**状态流转**：

```text
待源码审计
  -> 待迁移前确认
  -> 迁移中
  -> 待验证
  -> 待人工确认
  -> 已人工确认
  -> 下一功能可开始
```

以下情况必须暂停，不得进入下一功能：

- 当前功能尚未生成完整证据包；
- 自动测试、定向验证或 `git diff --check` 未完成；
- 存在未记录的兼容修改或未关闭的高风险项；
- 人工确认结果为“退回修改”或“暂不通过”；
- 人工确认人、确认时间或确认结论缺失。

**人工确认执行方案**：

1. 迁移执行者将任务状态改为 `待人工确认`，停止处理下一功能；
2. 在任务台账中补齐证据包索引：源仓库和完整 SHA、本地源码快照、原始 diff、目标变更、兼容修改、测试命令与实际结果、已知风险；
3. 向人工确认人提交结构化摘要，至少说明“迁移了什么、依据哪个源提交、改了哪些目标文件、验证是否通过、还剩什么风险”；
4. 人工确认人只能作出以下结论：`通过`、`退回修改`、`暂不通过`；
5. 只有结论为 `通过`，且台账已记录确认人、确认时间、确认说明和确认版本，任务才能标记为 `已人工确认`；
6. `退回修改` 或 `暂不通过` 时，任务保持当前功能范围，记录原因和下一步，不得切换到下一功能；
7. 通过后再由执行者更新台账并申请下一功能，不能在同一批次中预先迁移多个未确认功能。

**人工确认记录至少包含**：

- `task_id` 和 `global_feature_id`；
- 确认范围及源仓库固定 SHA；
- 本地源码快照和证据包路径；
- 确认人；
- 确认时间；
- 结论：`通过` / `退回修改` / `暂不通过`；
- 确认意见、遗留风险和后续限制；
- 确认时对应的目标分支基线或 commit。

### 3.4 选择标准

优先级按以下顺序判断：

1. 是否是当前主线缺失的真实业务能力；
2. 是否位于数据、策略、回测、持仓的依赖链上；
3. 是否可保留原始实现和原测试，而不是重写平行实现；
4. 是否有明确数据契约、权限、缓存和失败语义；
5. 是否能在低资源环境下进行定向验证；
6. 是否会改变金融口径、回测结果或持仓安全。

## 4. 分阶段迁移计划

### Phase 0：功能去重与基线审计

**目标**：把 15 个 Fork 的候选功能组收敛为全局功能清单。

**工作项**：

- 建立 `global_feature_id`，合并多个 Fork 中的同源功能；
- 拆分过大的 Walk-forward、微盘账户和研究功能组；
- 将文档、截图、任务归档、生成文件和纯工程维护降级或排除；
- 检查每个候选功能的主线重叠、依赖文件、许可证和原始测试；
- 为每个候选项标记 `P0/P1/P2/P3` 和迁移状态。

**验收**：所有纳入分母的功能都有原始 SHA、路径、主线差异、依赖和验收标准；未完成去重前不迁移大批量代码。

### Phase 1：数据底座与数据源

**目标**：先稳定策略、因子和回测共同依赖的数据口径。

**功能范围**：

- AkShare、通达信/TDX、`eltdx`、Stock SDK、Fuyao、自定义数据源；
- 数据源能力矩阵、优先级、回退和插件加载；
- 日 K、分钟 K、实时行情、交易日和历史回补；
- ETF 行情、五档盘口、深度数据；
- 除权、复权、原始价/复权价和增量恢复；
- 资金流、ETF 份额、两融、南向和扩展数据；
- 脏数据、空表、缺列、分区和新鲜度保护。

**主要原始证据候选**：

- `CJXkeep/tickflow-stock-panel`：AkShare 数据源；
- `mygx-xx/tickflow-stock-panel`：`eltdx` 与集合竞价回填；
- `jie429/tick-stock-panel`、`kuku-26/tick-stock-panel`：ETF、分钟和数据契约修复；
- `flyme8899/tick-stock-panel`：资金流回补与来源优先级；
- `m01i0ng/tick-stock-panel`：日内扩展数据与复权口径修复。

**验收**：数据源能力、交易日、复权、历史回补幂等性、空数据和失败路径通过定向测试；不同源切换不能改变上层数据语义。

### Phase 2：策略、指标与因子

**目标**：在统一数据口径上迁移策略和因子能力。

**功能范围**：

- 自定义策略、自定义信号和策略种子；
- `overlay_filter` 叠加条件和条件编辑器；
- 策略读取指数/ETF 日 K；
- 策略安全校验、策略 ID/阈值配置；
- 策略生命周期、发布、归档和绩效淘汰；
- 指标、因子、Alpha 研究和因子缓存；
- 盘中 enriched 数据、非有限值和缺列保护；
- 监控条件与策略条件复用。

**主要原始证据候选**：

- `mygx-xx/tickflow-stock-panel`：策略生命周期、因子和数据缓存；
- `jie429/tick-stock-panel`、`kuku-26/tick-stock-panel`、`m01i0ng/tick-stock-panel`：ETF/指数读取、overlay filter、策略安全修复；
- `flyme8899/tick-stock-panel`：因子研究结论和资讯策略联动。

**验收**：策略 JSON 兼容、信号 CRUD、条件安全、指标口径、缺数据行为和未来数据隔离全部通过测试。

#### Phase 2-A：现成策略集成

**目标**：优先审计并迁移已经在 Fork 中形成独立源码文件的策略，避免先重写策略框架或另行设计平行实现。以下条目是源码级候选，不代表已经通过当前主线的加载、数据和回测验证。

**实施规则**：

- 以 Fork 原始源码和配套提交为优先输入，先建立源码快照和提交关联，不直接复制整个 Fork；
- 迁移目标是当前运行时的 `data/strategies/custom/` 契约，必须通过 `META`、策略安全校验、参数归一化和策略注册；
- 先完成单策略隔离验证，再决定是否加入策略种子或默认策略列表；
- 不因“策略可以加载”而认定策略有效，必须补充固定样本选股结果、回测结果和未来函数检查；
- 如果候选策略依赖当前主线不存在的数据字段或涨停口径，标记为 `阻塞`，先迁移数据契约，不在策略中偷偷补造数据。

**Phase 2-A 验收**：每个策略均有 `global_feature_id`、原始 SHA、本地源码快照路径、原始 diff、配套测试、源码路径、数据依赖、参数表、加载结果、固定样本输出、回测结果和风险结论；未通过未来数据隔离、缺列保护或回测一致性验证的策略不得进入后续持仓或自动执行流程。

#### Phase 2-B：策略框架增强

**目标**：在现成策略完成兼容性审计后，再迁移影响多个策略的通用能力。

**候选范围**：

- cooldown 冷却参数：`e96cb375efe00cc0a01f3643c470e3d776f52296`、`cb67dd928e7ea4411d251e3b31f8b167503a58a9`；
- 连续亏损后的暂停机制；
- 策略生命周期、发布、归档和绩效淘汰；
- `overlay_filter`、自定义信号和组合策略增强；
- 策略回测详情、因子缓存和研究结果联动。

**验收**：框架增强必须有明确的向后兼容行为，不能改变既有策略的默认信号；冷却、暂停和绩效淘汰必须覆盖边界状态、重启恢复、权限和审计记录。

### Phase 3：回测与研究

**目标**：迁移可复现且不产生未来函数的回测和研究能力。

**功能范围**：

- Walk-forward 的 IS/OOS 滚动窗口；
- 折有效性、前视泄漏、方向退化、NaN 序列化和净值曲线；
- 因子回测、IC、分层和默认区间；
- 回测历史、panel cache、single-flight 和并发缓存；
- 分钟填充内存控制；
- 回测的复权、交易日、成交价、手续费和滑点口径。

**主要原始证据候选**：

- `jie429/tick-stock-panel`、`kuku-26/tick-stock-panel`、`m01i0ng/tick-stock-panel`、`arcytan/tick-stock-panel`：Walk-forward、ETF 回测、panelcache 和回测默认区间；
- `halolauxu/tick-stock-panel`：分钟回测内存和研究型回测约束。

**验收**：IS/OOS 分离、无未来函数、回测结果可重复、缓存并发安全、大数据量内存受控；失败不得产生伪成功结果。

### Phase 4：持仓、模拟盘与风险

**目标**：在策略和回测语义稳定后迁移账户、持仓和模拟执行。

**功能范围**：

- 多账户、现金、持仓、订单、成交和结算；
- 模拟盘净值、历史持仓和组合 REST API；
- 监控事件触发模拟订单；
- 自动买入、问财模拟和成交幂等；
- 最大持仓、参与度预算、资金占用和微盘股风险；
- 策略信号到订单的权限与确认边界；
- 旧账户 JSON、订单和持仓数据迁移。

**主要原始证据候选**：

### Phase 5：监控、AI 与前端集成

**目标**：最后接入依赖前述稳定契约的上层体验。

**功能范围**：

**验收**：权限和确认流程不被绕过；扩展失败隔离；空、错、加载、窄屏和深色状态完整；AI 调用可追溯。

### Phase 6：部署、升级与发布

**目标**：在业务功能稳定后收敛运行时和发布能力。

**功能范围**：

**验收**：app-only 和 DSA profile 静态解析、低资源环境构建/启动条件、数据目录权限、旧配置读取、可选能力降级和 CI 全部明确。

## 5. 依赖关系与批次门禁

```text
Phase 0
  -> Phase 1 数据底座
      -> Phase 2 策略/指标/因子
          -> Phase 3 回测/研究
              -> Phase 4 持仓/模拟盘/风险
                  -> Phase 5 监控/AI/前端
                      -> Phase 6 部署/发布
```

- 所有 Phase 进入实施前，必须先完成相关源仓库的本地源码快照和固定 SHA 校验；
- Phase 1 未通过数据契约，不迁移策略或因子；
- Phase 2 未通过未来数据和策略安全测试，不迁移回测；
- Phase 3 未通过资金、成交和回测口径测试，不迁移持仓；
- Phase 4 未通过幂等和风险约束测试，不接入自动执行；
- Phase 5 不允许前端绕过后端权限、缓存或数据标准化；
- Phase 6 不把部署修复反向混入业务功能批次；
- 前一功能未达到 `已人工确认`，不得进入同一 Phase 的下一功能。

每个 Phase 进入实施前必须重新确认本批功能范围；范围变化或出现主线不兼容时暂停并更新本计划。

## 6. 验证矩阵

| 范围 | 最低验证 |
|---|---|
| 数据源/数据底座 | 能力矩阵、空数据、缺列、交易日、复权、历史回补幂等、失败降级 |
| 策略/因子 | 策略 JSON 兼容、自定义信号、候选策略加载、参数契约、固定样本输出、缺数据、非有限值、未来数据隔离、权限 |
| 回测 | IS/OOS、未来函数、手续费滑点、复权、交易日、缓存并发、内存边界 |
| 持仓/模拟盘 | 多账户、订单幂等、现金和净值、删除隔离、风险约束、旧数据迁移 |
| AI/监控 | tool call 追踪、确认卡、事件去重、失败隔离、通知失败路径 |
| 前端 | 加载/空/错/切换/实时刷新、窄屏、深色、扩展异常边界 |
| 迁移前用户确认 | 迁移意义、预期收益、范围、风险、来源和验证方案已说明，用户明确确认并记录 |
| 人工确认 | 证据包完整、范围明确、风险已说明、确认人/时间/结论/基线已记录，且通过后才允许下一功能 |
| 部署 | Compose 解析、数据目录权限、app-only、DSA、旧配置、低资源约束 |

验证命令必须记录实际结果，不把计划执行的命令写成已通过。

## 7. 许可、依赖和兼容风险

- 不整体覆盖 `pyproject.toml`、锁文件、Dockerfile 或 Compose；只迁移批准功能所需的最小变更；
- 第三方数据源、vendor、二进制和图片必须核对许可证与声明；
- 数据源新增必须先核对能力声明、单位、复权、交易日和空值口径；
- 策略/因子新增不得绕过统一 enriched 数据和安全校验；
- 现成策略候选必须先核对原始源码、测试、数据字段、涨停/复权口径和许可证，不得仅凭提交标题直接纳入默认策略；
- 回测和持仓新增不得引入未来函数、错误成交或静默降级；
- 不将美股/加密资产 Fork 的资产假设直接套到 A 股；
- 不把 Fork 中已有的上游代码重复迁移；
- 所有源码变动以已下载并固定版本的功能关联仓库源码为准，禁止无证据平行重写；
- 不能拆开的附带功能或依赖必须扩大范围后再实施；
- 低内存主机上的构建、测试和 Docker 验证必须单进程、单并发并遵循仓库资源门禁；
- 未完成人工确认的功能不得被视为完成，不得与下一功能并行迁移。
