# 迁移总索引与进度口径

## 文件与职责

- 总索引：`docs/integration/migration-registry.md`，集中记录迁移过、正在迁移和待确认的仓库。
- 每个仓库一条记录；每轮迁移关联自己的 `docs/integration/<移植标识>-migration-plan.md`，旧轮次与计划路径保留，不被新轮次覆盖。
- 总索引用于发现仓库与展示摘要；详细功能状态、源码文件来源、确认范围、验证证据和迁移历史以对应计划为准。两者不一致时报告差异，查询时不自动修复。
- 初始化只在获准建档/迁移的范围内执行，建立带标题的 Markdown 文档，使用下述仓库总览和各仓库轮次记录格式；没有记录时写“暂无迁移记录”，不填示例仓库。索引缺失不证明没有历史迁移；先只读查找现有计划，恢复索引须获授权，不凭聊天记录虚构已完成项。

## Markdown 记录格式

总索引使用 Markdown，不使用 JSON 或嵌入 JSON。包含两层记录：

### 仓库总览

每个仓库一行，列为：**仓库标识、仓库地址、移植标识、活动/最近轮次、状态、代码进度、验证进度、计划文档、更新时间**。

- 仓库标识使用规范化的 `host/owner/repo`，用于查重；地址不含凭据。
- 代码与验证进度分别写为“已完成数/确认总数（百分比）”；尚未确认时写“待确定”。
- 计划文档使用指向当前轮次计划的 Markdown 相对链接。从总索引链接计划时使用同目录文件名，解析后必须对应 `docs/integration/<移植标识>-migration-plan.md`，不能形成重复的目录路径。
- 总览展示所有活动轮次（含各自状态、进度和计划链接）；无活动轮次时展示最近轮次。不同轮次不混算百分比，历史已完成轮次仍保留在下面的仓库记录中。

### 各仓库轮次记录

每个仓库一个独立标题区块，包含稳定移植标识、仓库地址、创建时间及各轮次子标题。每轮保留：

- 唯一轮次标识及计划文档链接。
- 状态：规划中、待确认、迁移中、阻塞、代码已移植、已验证、已取消、无需迁移。
- Fork 分支、固定源码完整 SHA、源码提交时间；上游比较 SHA、目标分支及基线 SHA。
- 用户确认范围和确认时间；未确认写“待确认”。
- 确认范围内功能总数、代码已移植数、验证通过数，以及对应百分比。
- 更新时间、阻塞原因和下一步。

所有时间带时区；未知快照写“待获取”，未确定的计数/百分比写“待确定”，零项范围写“不适用”。不得填猜测值，不将分支 HEAD 或 commit 个数充当功能进度。历史轮次追加保留，不覆盖旧记录。

## 场景一：查看当前迁移进展

1. 只读加载总索引，列出各仓库及轮次状态，通过记录的计划文档链接核对实际功能状态。
2. 展示已完成的历史轮次及正在进行的轮次：仓库、状态、代码移植百分比、验证百分比、已完成/总功能数、计划路径、更新时间、阻塞和下一步。
3. 仓库有已完成历史但当前正在增量迁移时，同时报告两者，不能简单归为“已迁移完成”。
4. 索引缺失、计划缺失、统计不一致或记录过期时明确说明；不自动 fetch、建档、修复文件或继续迁移，不把未记录视作 0%。

## 场景二：新仓库迁移与查重

1. 将 HTTPS/SSH Git 地址规范化：去掉 `.git`、尾斜杠，将 GitHub 的 host/owner/repo 小写；不同协议的同一仓库使用同一 key。其他托管平台按其大小写语义处理。若存在改名、转移或同名歧义，核实后再合并记录。
2. 查总索引及现有计划。存在相同 key 时，不创建重复仓库记录：先按源分支、目标分支和用户确认范围匹配轮次，匹配的未完成轮次优先续接；不同分支/目标的任务独立记录。新的源码快照或新确认范围新增轮次并保留旧计划和历史。存在多个候选时请用户选择，不自动切换分支或混用计划。
3. 不存在时，在用户允许写入的范围内创建计划文档和一条仓库记录，初始状态“规划中”，百分比“待确定”。建档与确认计划不等于允许执行功能移植。
4. 文档路径使用 `docs/integration/<移植标识>-migration-plan.md`；增量轮次在标识中加入唯一轮次后缀。先写计划，再更新索引；任一步失败都报告，不留下伪造的完成状态。

## 场景三：实施与进度更新

- 对计划内功能分配稳定功能 ID，按同一口径计数；无需移植、排除、取消项不进分母。功能拆分/合并或范围改变须先确认，记录范围版本及变化原因，禁止通过调整分母虚增进度。
- 已确认功能总数 `N > 0` 时：`code_percent = round(100 * code_migrated / N, 1)`，`verified_percent = round(100 * verified / N, 1)`。每项功能最多计一次；已验证项也计入代码已移植。满足 `0 <= verified <= code_migrated <= N`。
- 未确认范围、无法确定总数或 `N = 0` 时，两种百分比显示“待确定”或“不适用”；确认无功能需要迁移则标为“无需迁移”，不显示虚假的 100%。
- 每项实施结束、发生阻塞或验证后：先更新详细计划及历史，再从实际功能状态同步本轮索引。代码全移植但验证不全时标为“代码已移植”，不得标记“已验证”；有阻塞时保留真实已完成计数并标明“阻塞”。
- 完成指用户确认范围内全部功能验证通过，不代表移植了 Fork 的所有功能；摘要必须说明范围。未 commit/push 与迁移进度分别报告。
- 写入时保留其他仓库和旧轮次；检查 Markdown 表格/链接、仓库标识和轮次标识唯一性、计划路径及计数约束，再以临时文件原子替换，防止中断损坏索引。更新前重读文件，发现其他编辑者修改则核对后再写，不覆盖他人记录。

## 落地证据、续接与回退

- 每项功能在计划中记录目标路径和可复核的落地证据：直接复制文件的源/目标内容指纹、共同文件的合入 diff 或可重建差异记录；已提交时补充目标 commit SHA。未提交功能不得伪造提交 SHA。验证记录包含命令、结果、时间和被测文件版本/指纹。
- 续接检查当前目标分支、实际文件及证据。后续主线修改可能使指纹改变，不能仅凭不相等判为丢失；查看实际 diff 判断功能是否保留。无法确认时标明“待核实”，保留历史但不把不确定项算作当前完成。
- 文件删除、代码回退、分支 reset 或依赖改变导致功能丢失/验证失效时，先报告事实和重新评估的状态；只有获准更新记录后才同步计划与索引，并追加事件时间、原因及受影响项。不得自动恢复代码或执行回退。
- 功能代码确实丢失则不计代码完成，代码仍在但验证失效则不计验证完成；历史测试结果保留并注明仅对旧版本有效。因纠错而降低计数属于如实修正，不属于擅自改变确认范围。
- 源码更新删除功能、重命名文件或引入数据迁移时，计划明确动作、依赖和兼容/回退方案。删除文件、修复数据、停服务等操作须获相应明确授权；原测试不能替代目标主线回归。

## 索引与计划更新中断恢复

- 计划是事实依据，索引是摘要。查询发现计划已更新而索引未同步时，只报告差异和可核实进度，不自动修复；记录缺失不代表功能未移植。
- 获准恢复记录后，先核对计划与实际代码、落地证据，再从计划重算摘要，保留其他仓库和旧轮次；只恢复文档，不重新执行已完成的代码迁移。
- 计划缺失或多个记录冲突时，不用索引摘要重建虚假的详细完成状态；列出缺失和冲突，请用户决定恢复方案。

## 百分比说明

百分比是本轮用户已确认功能项的完成比例，不代表代码量、耗时、剩余工作量或整个 Fork 的迁移比例。大型模块与小功能均按计划的稳定功能 ID 计数；展示时附范围说明，不跨轮次合并分母。
