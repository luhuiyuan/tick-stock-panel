# Fork 原代码迁移

在项目根目录执行操作。遵守根目录 AGENTS.md、CONTRIBUTING.md 和涉及二次开发时的 docs/secondary-development.md；本技能不授予 fetch、文件修改、清理、构建、提交或推送权限。

## 按需读取

- 查询“当前迁移进展”、开始新仓库迁移或更新进度时，先读 [迁移总索引与进度口径](references/migration-registry.md)，再读取 `docs/integration/migration-registry.md` 及其中关联的计划文档。查询只读，不自动建档或迁移。
- 计算或复核独有提交、准备新 Fork 的计划时，先读 [提交计算与中间文件](references/commit-analysis.md)，使用项目现有脚本，不自行用 SHA 差集替代 patch-id 匹配。
- 继续已有迁移时，通过总索引定位对应的 `docs/integration/<移植标识>-migration-plan.md`，核对分支和工作区，再按已确认计划继续；仅需要复算时读取上述参考文件。

## 主流程与记录要求

- 首次迁移或开始新轮次时，先在用户授权范围内获取待移植 Fork 和上游源仓库的最新代码；检查 remote 地址，优先复用现有 Git 仓库 fetch，不重复 clone。记录仓库、分支、获取时间和双方完整 commit SHA，并以固定 SHA 作为本批移植基准；不得擅自 merge、reset 或覆盖工作区。中断续接使用原已确认快照，不因远端更新自动换基准；变更快照须重新评估并确认计划。
- 先按 commit SHA 精确匹配，再按 `git patch-id --stable` 匹配；不要求共同祖先。Fork 侧属于源作者身份的提交不能算 Fork 独有提交。merge 提交不直接当作独有功能，应单独检查额外的冲突解决改动；未匹配提交还须检查当前主线是否已实现同类功能。
- 必须以计算得到的 Fork 独有提交结果为依据，结合提交 message、实际 diff 和涉及文件识别新增或改动的功能列表；不能仅凭分支 ahead/behind 或 SHA 差集判定独有功能。为每项功能记录关联提交、主线现有能力、是否需要迁移及判定依据，并将同一功能的初始实现和后续修复归并，避免重复迁移。
- 修改功能代码前，必须建立并维护仓库内的持久化移植计划。各移植任务的计划统一放在 `docs/integration/<移植标识>-migration-plan.md`；文档创建和更新同样遵守方案确认规则，不能只靠聊天记录维护进度。
- 计划必须列出固定源码快照、功能范围、原始提交 SHA 和文件、后续修复、配套测试与 fixtures、配置与依赖、与主线重叠的文件、依赖顺序、分批方案、风险和验证方法。先提交完整功能迁移计划供用户确认，未经明确确认不得实施功能迁移；确认后按计划顺序逐项实施并更新进度，不擅自增加功能或调整范围。范围或行为发生重大变化时重新请求确认。
- 迁移文档必须保留 Fork 源码时间和可追溯的版本信息：仓库 URL、分支、固定快照完整 SHA、快照提交时间（含时区）、获取时间，以及各迁移文件在该快照中的原路径、最后修改提交 SHA 和提交时间。源码时间以 Git 提交信息为准，不以复制后的本地文件 mtime 代替；共同文件还须记录合入的原始提交及兼容调整，便于再次增量迁移。
- 迁移文档必须维护追加式迁移历史，记录每轮迁移日期（含时区）、起止源码快照 SHA 和时间、目标分支及基线 SHA、用户确认的计划范围、功能与文件、状态、兼容调整和验证结果；后续迁移不得覆盖或删除历史记录。再次迁移时先依据历史确定已迁移基准，再计算新增差异；已移植与未移植项分开核对，不能仅凭时间或分支 HEAD 推断迁移完成。
- 待移植仓库新增且当前主线不存在的模块在确认整文件所含功能均属于批准范围后，直接移植其固定快照的最终原文件及原测试；无法拆开的附带功能或依赖须先请求扩大范围，不能静默带入；共同文件只合入必要的独有变更，保留主线更新。配置、依赖和锁文件不得整体覆盖。不自写简化模块或平行实现来替代原功能；必要兼容调整须记录原因和改动位置。
- 进度表按功能区分“待移植、移植中、代码已移植、已验证、阻塞、无需移植”。每完成一批或发生阻塞、范围调整时立即更新文档，记录实际移植文件、原代码来源、兼容调整、已执行的验证及结果、未执行验证的原因、剩余工作和下一步。
- 每项功能保留目标文件及落地证据（未提交 diff/文件指纹，已提交时附目标 commit SHA），验证结果关联被测代码版本；详细要求见迁移总索引参考文档。
- 计划列明新增、修改、删除、重命名及许可/依赖/安装启动脚本风险；删除与状态变更遵守明确授权，不能整体覆盖或擅自回退。
- 每次继续移植或交接任务时，先阅读计划和进度文档，并核对当前分支、工作区与实际代码及落地证据；不能仅凭聊天摘要推断完成状态，避免遗漏或重复移植。
- “代码已移植”不等于“已验证”；优先使用原项目测试，并补足必要的主线兼容验证。未执行、失败或因资源不足暂停的验证必须如实记录，不得标记为通过。移植和文档更新均不代表获准 commit 或 push。

## 执行顺序

检查总索引并定位已有记录（新仓库获授权后建档） → 新轮次获取并固定源码快照（续接保留原基准） → 脚本计算独有提交 → 根据 message、diff 和文件归并新增/改动功能 → 写入功能迁移计划 → 等待用户确认 → 按依赖逐项移植原代码和原测试 → 记录兼容调整与实际验证 → 更新计划进度、同步总索引和追加迁移历史。

有阻塞、范围扩大或行为改变时停止并说明，不通过自写替代实现绕过。结束时报告已移植、已验证、未验证及剩余项；不自动 commit 或 push。
